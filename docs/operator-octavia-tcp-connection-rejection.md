# Proportional TCP connection rejection

Set `--octavia-tcp-connection-rejection` on the Gateway controller to enable this mode for plain TCPRoute listeners on either Gateway API v1.7.0 channel. The flag defaults to off. The regional Amphora endpoint must advertise `tcp_connection_rejection_v1` and return the `tcp_connection_rejection` field in its pool inventory. Enable the flag only in regions where the API, worker and serving Amphora data path support the extension. The GatewayClass continues to define the Service member mode and backend network.

With two backendRefs of weights 3 and 1, withdrawing the second reference's ReferenceGrant makes the controller reserve 1 out of 4 new connections for active rejection. The valid Service receives the other 3 out of 4. Its eligible real members share that traffic using the existing Endpoint or NodePort weighting. A missing Service, a Service incompatible with the bound member mode, or a Service with no eligible endpoints also contributes its positive weight to rejection. A zero-weight reference still contributes reference diagnostics. When every positive weight is invalid, the serving pool has no real members and rejects every new connection.

The controller waits for Octavia provisioning and checks the observed members and rejection share before reporting the route programmed. An invalid reference can keep `ResolvedRefs=False` while the route's `<controller-domain>/Programmed=True` confirms that forwarding and rejection are installed. A Service with no eligible endpoints can still have a resolved reference. Kubernetes read failures, uncertain topology and Octavia health checks do not create a weighted rejection share. If authorization is withdrawn while safe programming cannot be confirmed, the affected default is withdrawn.

When an attached pool is ready for the change, the controller sends the complete authorized member set and rejection share in one Octavia member-batch update. Newly created pools are staged before attachment. During rollout or an authorization change, an unconfirmed target may be withdrawn until its graph and checkpoint can be verified. After an interrupted update, the controller can retry a matching pending batch with backoff or submit the current authorized replacement once the load balancer accepts updates again. Rejection applies to new connections. A connection established before a graceful reload can persist.

Modify a test route with two identifiable backend responses to verify the region after rollout. Open fresh TCP connections before withdrawing a grant, after confirmed provisioning, and after restoring it. Check that the revoked backend receives no new connections and the valid backend continues to receive its intended share. Include a route on another listener when qualifying a shared Gateway.

## Disable this mode

Keep the patched Octavia API and worker running while withdrawing the feature. Remove the flag from the controller deployment. A pool that can forward all desired traffic clears its stored fraction with an explicit null in the same write as its authorized members. When a route still has an unusable positive-weight backend, the ordinary fail-closed route withdrawal applies. Verify affected listener defaults and pool readback before reverting Octavia to a version that lacks the field.
