# Magnum opt-in for the OpenStack Gateway controller

This integration targets Magnum 23.0.0 and the magnum-capi-helm 1.4.0 source at `a8b82c2480a286a10b60ecc1d94c6cd9f1d01823`. A new cluster on an operator-selected template can run the controller alongside the stock OpenStack cloud controller. The addon manages five workload objects. The platform supplies the shared Gateway API CRDs, the OpenStackGatewayClassConfig CRD, the GatewayClass and its parameters, the workload namespace, and a dedicated Cloud Secret.

## Build and configure

1. Apply [the driver patch](../../../integrations/magnum-capi-helm/1.4.0.patch) to the exact upstream driver revision using `git apply --check` and `git apply`. Build the driver package using the normal Magnum operator packaging process. Deploy the same patched build and configuration to all conductors serving an opted-in template.
2. Mirror the exact Azimuth chart package to a read-only conductor directory as `openstack-cluster-0.10.1.tgz`. Verify SHA-256 `fa3c30070e6f9f6684bfb10641917089b5d8453d91bc566230544029a0380d9d`. Chart source revision `856f8fb` lists cluster-api-addon-provider 0.6.1 among its management dependencies. Verify that the management plane serves the `addons.stackhpc.com/v1alpha1` resource and can reach workload APIs. [Azimuth chart package](https://azimuth-cloud.github.io/capi-helm-charts/openstack-cluster-0.10.1.tgz), [management dependencies](https://github.com/azimuth-cloud/capi-helm-charts/blob/856f8fb7372615ac0d3173d9b5d91fe605c9aeac/dependencies.json)
3. From the reviewed controller revision, build the image and record its registry digest. Render the matching workload artifact with `kubectl kustomize integrations/magnum-capi-helm/workload > gateway-controller.yaml`. Place that file alongside the parent chart and record its SHA-256. The driver verifies both artifacts before handing the checked bytes to Helm. It substitutes the configured image digest and Magnum cluster UUID only.
4. Register a separate operator-owned cluster template with driver `k8s_capi_helm_v1`. Use `capi_helm_chart_version=0.10.1` on that template. Add its UUID to the conductor configuration. The allowlist selects new clusters only. Existing stock clusters on that template continue to resize, upgrade and delete through the stock path. Enrolled clusters carry their recorded addon state across allowlist changes and compatible template upgrades. Apply allowlist changes consistently across conductors and let in-flight creates complete before changing eligibility.

```ini
[capi_helm]
gateway_api_cluster_templates = <operator-template-uuid>
gateway_api_artifacts_dir = /srv/magnum/gateway-addon
gateway_api_manifest_sha256 = <gateway-controller-yaml-sha256>
gateway_api_controller_image = registry.example.test/gateway/controller@sha256:<image-sha256>
```

## Create and qualify a workload cluster

1. Create a workload cluster from the selected template. Before saving the stock Helm release name or creating any provider credentials, the driver creates `gateway-enrollment-<cluster-uuid>` and `gateway-addon-<cluster-uuid>` in the Magnum management project namespace. Both immutable Secret records hold the cluster UUID and workload credential reference. The first records enrollment independently of the second, which carries the teardown acknowledgement. The pinned chart also annotates the managed CAPI Cluster with `gateway-api-openstack.github.io/enrolled-cluster` and the UUID. Restrict record writes and deletes to the conductor and authorised operators. Back up both records.
2. Access the new workload API using the management-plane CAPI kubeconfig procedure as soon as it comes up. Create or verify the reserved workload namespace `openstack-gateway-system`. Install the Gateway API bundle supported by the chosen image and the controller's own CRD through the platform's usual owner. Set their versions from that exact controller revision. Keep both CRD owners independent of the addon. The addon's install waits for a runnable controller and can time out while these prerequisites are missing.
3. Provision an application credential dedicated to this workload cluster in its OpenStack project. Scope it to the Octavia and Neutron operations required by the chosen class. Use the existing site credential delivery mechanism to create `openstack-gateway-system/openstack-clouds` in the workload cluster. Supply the `clouds.yaml` key with an `openstack` entry, the correct region and validated TLS trust. For a private CA, add its PEM bundle to the same Secret and set `cacert` in the `openstack` entry to its mounted path, such as `/etc/openstack/ca.pem`. The application credential used by CAPI and OCCM stays separate. Helm receives the workload Secret name, and the Deployment projects all keys into `/etc/openstack`. Protect workload Secret and controller Pod access.
4. Check that the management `Manifests` addon `<release-name>-openstack-gw` reports `Deployed` and the workload Deployment `magnum-openstack-gateway-controller` is ready. The addon targets `openstack-gateway-system` with Helm release `openstack-gw`. Its payload contains a ServiceAccount, a ClusterRole, a ClusterRoleBinding, a ConfigMap, and a Deployment with the `magnum-` prefix. Reserve those object names for this release.
5. Create a platform-owned GatewayClass with controller name `gateway-api-openstack.github.io/magnum-gateway`. Configure the first class for a private Amphora VIP, its member subnet and a NodePort backend. Verify current-generation GatewayClass, Gateway and HTTPRoute status and a known response through the VIP. Confirm that the API server and OCCM Service LBs keep their own identities. The Magnum status includes addon deployment, while traffic and provider ownership need independent checks.

## Rotate the dedicated credential or update the controller

Keep the old credential valid during replacement. Use the site credential delivery mechanism to update the same workload Secret with the replacement `clouds.yaml` and any CA bundle it references. Verify the intended keys and explicitly remove any retired CA key. Applying `stringData` with a key omitted can leave the old key in `data`. Restart the Deployment so the controller reads the new inputs at startup. Verify readiness, OpenStack authentication against the original project and endpoints, and a known response through an existing Gateway before retiring the old input. Magnum credential rotation acts on CAPI's separate credential.

Qualify an image update and recovery with the same controller name and cluster UUID. To restore the previous controller version, restore its reviewed image digest and matching verified workload artifact in conductor configuration, then re-render through a planned Magnum resize or compatible template upgrade. The dedicated Secret is separately managed and keeps its current inputs. Verify that the recovered controller authenticates with those inputs and that the existing Gateway still serves traffic.

## Drain before disable or delete

Active markers cause Magnum delete and final cleanup to stop before Helm or credential removal. Compatible template upgrades preserve the addon while it is active. Retain the management addon, workload API, controller, both records and dedicated credential when any drain step fails.

1. Fence allocation at the workload API. Keep the existing GatewayClasses with controller name `gateway-api-openstack.github.io/magnum-gateway` while their Gateways finalize. Block creation of new classes with that controller name or changes which would make another class select it. Use the site's admission control to deny new Gateways selecting the affected class names and deny changes by tenants or automation to those Gateways and to HTTPRoute and TCPRoute attachments targeting them. Preserve DELETE access and the addon ServiceAccount's reconciliation and finalizer updates. Pause provisioning automation and verify with rejected workload API writes. Keep the fence through addon removal or workload API teardown.
2. Record the affected Gateway, HTTPRoute and TCPRoute bindings and their immutable UIDs, then delete the affected Gateways and let the controller finish finalization. Remove only dedicated tenant objects you own. Keep shared Gateway API objects and shared HTTPRoutes in place. Inspect stuck finalizers and the original cloud project or region using the [controller recovery guide](../../operator-recovery.md).
3. Under the verified fence, run the recovery guide's read-only `openstack-gateway-audit` with controller name `gateway-api-openstack.github.io/magnum-gateway`, the Magnum cluster UUID, the original project and region, and Octavia microversion 2.5. Verify a complete result with no remaining cluster-owned resources or unresolved bindings. Check the audit's discovery limits against the recorded UIDs and provider inventory, including pending Octavia operations and Neutron resources. Investigate any unexplained absence or ownership conflict. With a lost workload API, preserve the credential and establish an equivalent maintenance fence and identity-scoped OpenStack inventory with the management operator. Keep teardown blocked whenever ownership, absence or the fence cannot be established.
4. Record a private teardown report identifying the cluster UUID, controller, project, region, credential reference, verified fence and cloud audit evidence. Annotate the exact cluster marker in the management project namespace with the digest of that report. This is an operator acknowledgement that the fence is in force and the owned inventory is empty. The driver validates marker ownership and the digest format. Site operators verify the evidence itself.

```sh
kubectl --context <management-context> -n <magnum-project-namespace> annotate \
  secret gateway-addon-<magnum-cluster-uuid> \
  gateway-api-openstack.github.io/cleanup-evidence=sha256:<teardown-report-sha256>
```

5. Run normal Magnum delete, or let the next planned Magnum resize or compatible template upgrade re-render without the addon. Confirm management addon removal and the workload release's absence if retaining the cluster. Retire the dedicated credential and its Secret after these observations. For a deleted cluster, retain both records until Magnum reports `DELETE_COMPLETE`, then remove them separately. A retained cluster keeps its drained records and stays disabled through later updates. Direct Helm rollback, record manipulation or management-resource deletion bypasses this workflow.

## Recover missing enrollment records

An enrolled cluster with a missing or invalid record is held for recovery before the driver changes its template, rewrites Helm or starts destructive teardown. A `CREATE_FAILED` cluster with no saved release name can follow stock cleanup, because the driver saves that name before creating provider credentials or running Helm. A delete arriving during a selected cluster's pre-release create is rejected. Magnum can record `DELETE_FAILED` while the create worker is still running. If the state persists without a release name, confirm the original create is no longer running and follow the scoped recovery and drain acknowledgement before retrying.

1. Confirm the exact Magnum cluster UUID, management project namespace and release name from authoritative Magnum inventory. Match the surviving enrollment record, addon marker, CAPI Cluster annotation or protected backup to that identity. An allowlisted template or a shared project alone cannot establish enrollment.
2. Restore only the missing or invalid records in that management namespace from the protected backup. Each record must be an immutable Secret with label `gateway-api-openstack.github.io/cluster-uuid` set to the UUID and data keys `cluster-uuid` and `credential-reference`. The decoded values are the original UUID and `openstack-gateway-system/openstack-clouds`. If reconstructing from a surviving identity, restore the marker as active by leaving its cleanup annotation absent.
3. Retry after re-reading both records and validating their identity. Establish the allocation fence and run a fresh scoped ownership audit before acknowledging any drain that cannot be verified from a preserved report. If all enrollment evidence has been lost or conflicts, keep management and cloud actions on hold while recovering backup or reconciling the original cluster's provider inventory. The driver can detect a lost pair from the live CAPI Cluster annotation. Recovery after loss of all copies requires operator evidence.

## Offline evidence and limits

Use the standard upstream test module in the patched Magnum driver checkout with the two artifacts above and Helm 3.19.4.

```sh
MAGNUM_TEST_ARTIFACTS=/path/to/artifacts MAGNUM_TEST_HELM=/path/to/helm \
  python -m unittest magnum_capi_helm.tests.test_gateway_api
```

The render test captures the pinned driver's Helm arguments and JSON values, renders the published parent archive with the addon off and on, and checks the controller objects, dedicated Secret projection and CAPI enrollment annotation. Tests also cover legacy stock operation, early create failure, missing enrollment state during upgrade and the teardown hold and acknowledgement. The local lifecycle rehearsal exercised Helm install, upgrade, rollback and uninstall on a Kubernetes API server. A separate TLS test initialized the same Go client factory used at controller startup with the replacement files. Live install, traffic, provider isolation, rotation, interrupted operations, rollback and teardown remain pending. [Results of both rehearsals](magnum-driver.md#local-lifecycle-rehearsal)
