# Certificate mapping and shared HTTPS frontends

**Operator-managed mode.** The operator enrollment helper binds a Kubernetes Secret revision to an immutable Barbican PKCS#12. The controller accepts one HTTPS listener per physical port in the opt-in installation. The default workload installation grants no Secret access. [Operator runbook](../../../operator-https.md) · [Helper and map format](../../../../hack/operator-certificates/README.md)

An earlier stock Octavia fixture served eight fresh HTTPS requests across two operator-provisioned PKCS#12 revisions. Its Keystone identities, provisioning transitions and Amphora agent were simulated. Multiple HTTPS sections sharing one port remain a separate design question. [Stock HTTPS provider evidence](stock-https-rotation.md)

**Ownership.** Keep the allowlist in protected deployment configuration, scoped to the class, cluster and destination project. Tenants supply only a standard Secret reference. Ignore cloud references from tenant objects. Bind namespace, name, Secret UID and revision to a Barbican secret UUID. Build the URI from the authenticated key-manager catalog endpoint for the configured region and interface. Establish project ownership from the operator’s project-scoped creation receipt. ACLs can allow a successful cross-project read. [Catalog selection](https://github.com/armeldemarsac92/gateway-api-openstack/blob/d15f0b32c79864237e1ecc47777d22da0ae7b9d8/internal/cloud/openstack/clients/keymanager_test.go) · [Barbican 23 project handling](https://github.com/openstack/barbican/blob/1efe16cd73b6e7d7c827aa8090665f2564de632e/barbican/api/controllers/secrets.py#L154-L168)

A trusted provisioner needs access to both payloads. It must parse the TLS Secret, verify its key matches the leaf, and establish that the uploaded PKCS#12 contains the same leaf, ordered intermediates and corresponding private key. Bind that verification to the exact revision. The reconciliation process needs an approved way to observe the current UID, revision, deletions and grants. Names, Secret type, Barbican metadata and a handshake alone cannot establish the entire pairing. Operator ownership covers provisioning, Octavia access, rotation, retention and deletion. [Immutable payload](https://docs.openstack.org/api-guide/key-manager/secrets.html)

Check cross-namespace permission in the Secret namespace before lookup. On revocation, withdraw affected serving configuration, including any default certificate that would expose revoked material, and set listener `ResolvedRefs=False/RefNotPermitted`. An authorized missing or malformed Secret gets `InvalidCertificateRef`. A missing mapping blocks programming. A recreated UID needs fresh authorization. After an ambiguous update, recheck current intent and ownership, fetch the recorded listener, wait for `ACTIVE`, compare the reference and verify the expected leaf and chain on a fresh connection. Roll back only to an expressly authorized, valid revision. [Grant revocation](https://github.com/kubernetes-sigs/gateway-api/blob/e26d183dbbc1bb782b78addbd26faba03955c152/apis/v1/referencegrant_types.go#L35-L42) · [Listener reasons](https://github.com/kubernetes-sigs/gateway-api/blob/e26d183dbbc1bb782b78addbd26faba03955c152/apis/v1/gateway_types.go#L1749-L1788)

**Full tenant automation** additionally requires approved tenant-key access, cloud write and ACL privileges, durable revision ownership, interrupted-create recovery and retirement rules. Stock create assigns the ID and has no idempotency key. Metadata is written separately. Consumers register explicitly. An ambiguous create can leave an orphan, and an empty consumer list cannot justify deletion. Retain uncertain revisions for operator reconciliation. [Create](https://github.com/openstack/barbican/blob/1efe16cd73b6e7d7c827aa8090665f2564de632e/barbican/api/controllers/secrets.py#L469-L508) · [Metadata](https://docs.openstack.org/barbican/2026.2/api/reference/secret_metadata.html) · [Consumers](https://docs.openstack.org/barbican/2026.2/api/reference/secret_consumers.html)

**Qualification.** Four upstream HTTPS sections share one Secret and port. Preserve each section’s attachments and status. Prove exact hostname precedence over the most specific wildcard and then catch-all using distinct backend responses, including mismatched SNI and HTTP authority. The single-pool fixture cannot distinguish these outcomes. A trial could qualify operator-assisted rotation and routing for this shape. Core claims require the upstream cases and ordinary supported Secret behavior. Opaque TLSRoute passthrough needs ClientHello-based pool selection, which stock Amphora TCP lacks.
