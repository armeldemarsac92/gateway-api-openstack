# HTTPRoute path routing across Services

The controller can route different paths on one HTTPRoute to different Service ports and accept alternative paths within a rule. All rules on that HTTPRoute share its UID, parent status and Gateway writer. The following cases used the controller from image source `e17cf858d11d04cf35d298ad19d9498ccde6b491` in IPv4 endpoint mode. [Operator example](../../../getting-started.md#route-several-paths-to-services)

Each count reports the passing wire assertions out of six in the original Gateway API case. The order case uses three independent upstream echo Services and checks their identity in the response body. The two channels also ran concurrently while local checks and the image build were active. All six requests timed out at the original 30-second deadline in both parallel runs. In an individual run Standard reached all six backends. Experimental still reached the deadline. The ledger retains FAIL for both channels. The observations do not identify a sole cause for the timing difference. In the exact-path case `/one` and `/two` reached their respective applications. Requests for `/`, `/one/example`, `/two/` and `/Two` received 503 at the stock listener. Gateway API requires 404 for all four. Two further original tests exercised invalid backend configurations. Both channels reported `ResolvedRefs=False/RefNotPermitted` for a prohibited cross-namespace Service. The HTTP assertion expected 500 and observed 503. An HTTPRoute with omitted and empty backend lists failed during parent acceptance. Separate requests then received 503 on all three paths, including the one healthy forwarding rule. The archived receipts distinguish those fresh requests from the upstream subtests.

## Lifecycle

In two concurrent 120-second lifecycle runs, migration produced six policies and three pools, but the broad prefix still returned 503 at the deadline. In separate runs the same source reached the expected backends and completed the lifecycle. The individual fixture waited for Kubernetes conditions before enumerating all provider children. The measurements changed concurrency and inventory polling together. They establish each outcome separately.

On each bundle the prior release created two single-path routes. The new controller adopted their existing provider resources, then changed one route to use multiple Services. Replacing a Service and adding an alternative match sent the next requests to the named backend. Removing its cross-namespace ReferenceGrant set `ResolvedRefs=False/RefNotPermitted` and disabled the two addressable members of that Service through Octavia. Fresh requests to the withdrawn prefix and its child received 503. Healthy siblings continued to return their expected echo identity. Restoring the grant reenabled the same member IDs. Gateway API requires 500 for the request that selects the prohibited backend.

A cold controller restart produced zero Octavia writes and retained all resource IDs. Deleting the changed route kept the sibling route serving traffic. Deleting the Gateway closed its frontend and preserved the unrelated load balancer. The receipts contain readback counts, status conditions and fresh probes for each phase. ## Environment and replay

The Kubernetes 1.36.2 API server used each genuine v1.7.0 bundle separately. The upstream tests, their manifests, the HTTP roundtripper and its deadlines came from `e26d183dbbc1bb782b78addbd26faba03955c152`. Stock Octavia 19.0.0 accepted the controller's public API writes, its Amphora renderer produced the configuration for HAProxy 3.0.19, and separate upstream echo processes answered over TCP. The harness supplies identity, network discovery, background task completion and the remote Amphora agent locally.
