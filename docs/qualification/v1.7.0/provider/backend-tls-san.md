# Backend certificate identities

A BackendTLSPolicy targeting an HTTP Service can accept a list of DNS or URI subject alternative names. The controller sends the configured backend hostname as TLS SNI. Amphora verifies the configured CA chain and requires a certificate identity that matches the policy. The regional capability must be available. [Octavia distributions](https://github.com/armeldemarsac92/octavia/releases/tag/hibiscus-backend-tls-sans-53db584246b1) · [Driver models](https://github.com/armeldemarsac92/octavia-lib/releases/tag/hibiscus-backend-tls-sans-7df306215a9e)

The upstream v1.7.0 case `BackendTLSPolicySANValidation` passed all six subtests on both release channels. The identical controller executable came from two reproducible linux/amd64 OCI builds. In each run the valid DNS, URI and multiple-identity routes reached the expected TLS echo pod with HTTP 200 and backend SNI `abc.example.com`. The three mismatched routes returned HTTP 503. After removal of the regional capability, all six policies reported `Accepted=False/UnsupportedProvider` and all six routes returned HTTP 503. The fixture runs real Kubernetes API servers and Pods, REST APIs from the published Octavia and Barbican packages, the Amphora configuration renderer and HAProxy. Keystone credentials and catalog, Neutron networking, RPC scheduling and the Amphora agent transport are simulated locally. Each report covers the selected Extended case of the GATEWAY-HTTP profile.
