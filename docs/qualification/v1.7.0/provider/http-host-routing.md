# HTTPRoute attachment by listener port and hostname

A parent reference can select multiple allowed HTTP sections on the same port. Each section matches the intersection of its hostname and the route’s hostnames. Route status counts the route once per section. The listener checks all those names when choosing between HTTPRoute and GRPCRoute attachments. This implementation requires the route’s selected sections to belong to one managed Gateway and one physical listener. [Distinct ports on one Gateway](http-distinct-ports.md) · [Sections with disjoint hostnames](http-disjoint-sections.md)

The first three cases used controller `3914abef6c37`, one disposable kind cluster per channel, upstream echo Pods, Octavia 19.0.1.dev12, octavia-lib 3.12.1.dev5 and Amphora-rendered HAProxy. The port test distinguished the hostnames on ports 80, 8080 and 8090. The Service test covered a Service with manually managed EndpointSlices, a headless Service and a headless Service with manually managed EndpointSlices. In the multi-route case, requests to `example.net` reached the selected backend. The plain request to `example.com/` exceeded its 30-second window on both channels. The request to that path with `Version: two` also exceeded its window on Experimental. [Standard receipt](http-host-routing-evidence/standard-kind.json) · [Experimental receipt](http-host-routing-evidence/experimental-kind.json)

In separate cold clusters, the original `HTTPRouteMatchingAcrossRoutes` ran on its own with `GOMAXPROCS=2` on the manager. It passed 8/8 on Standard and 8/8 on Experimental, with the original request deadlines. A separate request to `example.com/` after each case returned HTTP 200 on Standard and HTTP 200 on Experimental. [Standard receipt](http-host-routing-evidence/standard-isolated.json) · [Experimental receipt](http-host-routing-evidence/experimental-isolated.json)

The last two cases used the earlier released controller `577264d263de`, Octavia 19.0.1.dev6 and octavia-lib 3.12.1.dev3. The fixture ran five upstream echo processes. It populated Ready Pod status from their responses in a private Kubernetes API server without a kubelet. The rule-order case included the expected HTTP 500 for an invalid winning rule. The earlier controller rejected two effective route hostnames on Standard before any requests in `HTTPRouteMatchingAcrossRoutes`. [Matching receipt](http-host-routing-evidence/standard-envtest-HTTPRouteMatching.json) · [Rule-order receipt](http-host-routing-evidence/experimental-envtest-HTTPRouteRuleOrder.json) · [Earlier rejection](http-host-routing-evidence/standard-envtest-HTTPRouteMatchingAcrossRoutes.json)

Each local run used the public provider API and a native HAProxy process. Keystone, Neutron and worker completion came from the local fixture. The replay supplement gives the exact input revisions, hashes, source checkouts and per-channel commands.
