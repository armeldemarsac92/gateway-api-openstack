# Distinct HTTP ports on one stock Amphora Gateway

A Gateway can serve plain HTTP on several ports of one VIP. Requests to the same host and path can reach a different Service on each port. Octavia uses one HTTP listener per port with no default pool. Each HTTPRoute owns its forwarding policies and backend pool. A port with multiple Gateway listener sections requires distinct exact hostnames. A port with one section also accepts a wildcard or an omitted hostname. [Tenant example](../../../getting-started.md#serve-http-on-two-ports-of-one-gateway) · [Same-port sections](http-disjoint-sections.md)

Give each Gateway listener a distinct section name. An HTTPRoute can attach to all eligible sections through one Gateway parent reference. Use `port` or `sectionName` to narrow that selection. When both are set, they must match the same section. Each section checks the route kind, namespace policy and hostname intersection. By default a section accepts routes from the Gateway's own namespace. A route is counted once on each attached section, including when the sections use different physical ports.

Each port has its own forwarding policies. If a route selects HTTP and terminated HTTPS and the TLS certificate is unavailable, a ready HTTP listener can serve the route while the HTTPS listener stays closed. The controller's `Programmed` condition on that parent tracks all the selected ports. [HTTPS configuration](../../../operator-https.md)

Adding a port to an already bound Gateway enrolls it in per-port bindings and adopts the original listener in place. The controller keeps the original binding port recorded after a port is removed. Cleanup withdraws the policies for the retiring graph and verifies Octavia relationships before removing owned resources. The referenced frontend security group rules must already allow each desired port. As in the same-port case, the stock miss response observed in the local fixture is HTTP 503. Gateway API requires HTTP 404. [Proposed public response capability](octavia-http-local-responses.md)

## Traffic and cleanup

The Go provider test at `2b084bc00110b84155c2f8b6df03966186d8a771` reconciled against simulated Octavia and Neutron endpoints. It checked that adding the second listener preserved the first listener and its route resource IDs. A fresh adapter reconciled the same graph without writes. Stock Octavia templates rendered the recorded graph. Loopback HAProxy 3.0.19 returned HTTP 200 with different backend identities on both ports for `api.example.com /api`. After the original port was removed the old port refused a fresh connection while the remaining port returned the same backend response. Its listener, policies, pool and member stayed in place in the simulated inventory. The test also checked that disagreement about a retiring pool's associations held cleanup and that full Gateway deletion preserved the fixture controls. The separate stock Octavia 19.0.0 probe used the public v2 WSGI API, SQLite and a loopback VIP. Both ports served `same.example.test /app` and returned different backend identities. A request to `/other` got HTTP 503. Public listener deletion returned HTTP 204 and queued the stock Amphora listener deletion flow. After the flow ran, the old port refused connections while the sibling port still served its original backend. The stock API readback showed that the deleted listener and its policies and rules were gone. The old pool and member remained without a listener attachment. The integrated controller handles its own pool cleanup separately. [Stock probe receipt](http-port-results.json)

## Rollback

A two-version local check reloaded the current controller's stored Kubernetes objects into the preceding same-port controller at `d6278819244862c6dca7654ccc779f60622e62c9`. The earlier controller reconciled an unenrolled singleton through its recorded NodePort. It rejected both a two-port Gateway and an enrolled Gateway reduced to a single port. In each enrolled case, the Gateway reported invalid conditions and cleared its status address, route reconciliation reported a binding finalizer mismatch and the recording provider received zero calls. Separately the current controller requested cleanup and finalized the enrolled route and Gateway against the recording provider. [Compatibility and cleanup receipts](http-port-results.json)

Keep the current controller running while you migrate or drain traffic. Delete or detach the scoped routes, delete the enrolled Gateway, wait for finalization, and verify its owned resources and unrelated controls in the actual cloud. Recreate a supported single-port Gateway after restoring the earlier controller. The local check used a fake Kubernetes client and recordings. A deployed downgrade and VIP reuse remain unverified.
