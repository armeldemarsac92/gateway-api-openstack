# Discover an Octavia Gateway from Kubernetes

Enable the controller option `--gateway-infrastructure-metadata` to publish the private Octavia VIP of each managed Gateway through a headless Service in the Gateway's namespace. The Service has no selector. The linked EndpointSlice publishes the VIP and the ports the provider currently reports as programmed. HTTP, HTTPS, TCP and TLS use TCP Service ports. UDP uses UDP Service ports. Port names have the form `tcp-8080` or `udp-53`.

Use the standalone overlay `config/gateway-infrastructure-metadata` or the Magnum overlay `integrations/magnum-capi-helm/workload-gateway-infrastructure-metadata` to enable the controller flag and grant write access to Services and EndpointSlices. To combine this option with other controller features or Experimental CRDs, include the component `config/components/gateway-infrastructure-metadata` in your installation overlay. For Magnum, render the overlay as `gateway-controller.yaml` and pin the manifest checksum and the controller image in the conductor configuration. [Magnum operator procedure](qualification/v1.7.0/magnum-operator.md)

For a Gateway named `edge` in namespace `apps`, clients can use `gateway-edge.apps.svc` with their cluster DNS suffix. The name is `gateway-<Gateway name>` where that fits a Kubernetes Service name. For other names, the Service uses `gw-` followed by the first 32 hexadecimal characters of SHA-256 of the Gateway name. Clients still need network access to the private Octavia VIP and the listener port. When a listener uses HTTP hostname or TLS SNI matching, send the configured hostname or SNI while connecting to the address returned by DNS.

The controller copies `spec.infrastructure.labels` and `spec.infrastructure.annotations` onto the Service and EndpointSlice. The Gateway name and class labels use the original values when they fit in a Kubernetes label. Kubernetes discovery and controller identity keys are reserved. Independent metadata editors keep ownership of keys they add or change. `spec.infrastructure.parametersRef` continues to be rejected with `InvalidParameters`.

The controller withdraws the DNS endpoints when it observes the VIP is unassigned or the relevant listener is no longer programmed, and reuses the Service name when the VIP becomes available again. Gateway status follows the Gateway's address requests, which may include a Floating IP. A foreign EndpointSlice that names the discovery Service causes the controller to withdraw its Service until the conflict is cleared. The Service returns under the same name with a new Kubernetes UID. The controller leaves third-party objects untouched. Before disabling the controller option or withdrawing its write permissions, remove any discovery Service and EndpointSlice you no longer want to publish after verifying their owner references and controller annotation.

## Experimental ClusterIP addresses

With Gateway API v1.7.0 Experimental CRDs, add `--gateway-address-routability-cluster` to the controller arguments alongside `--gateway-api-channel=experimental` and `--gateway-infrastructure-metadata`. The existing infrastructure metadata component grants the required Service and EndpointSlice permissions. Enable this when the cluster's Service data plane can reach the private Octavia VIP and listener ports from Pods. Keep the ServiceCIDRs and Octavia VIP networks disjoint. For Gateways that only need cluster clients, select a GatewayClass configured without a Floating IP.

Add an `IPAddress` entry with `routability: Cluster` under `spec.addresses`. Each assigned Cluster address uses a separate selectorless Service in the Gateway's namespace. Omit `value` for a Kubernetes-allocated IP, or specify an available IP from a ServiceCIDR with the same family as the Octavia VIP. Read the assigned IP and its scope in `status.addresses`. A Gateway may also request its normal default address with a separate entry. The headless discovery Service retains its DNS name.

For a Gateway that only requests Cluster addresses, the controller reserves at least one Service IP before programming the Octavia frontend. If a replacement request cannot be fulfilled, a previously assigned ClusterIP can keep serving while the Gateway reports the new request as unassigned.

The controller withdraws the ClusterIP Services when the last Cluster request is removed. To disable ClusterIP publication, remove the Cluster requests, then remove `--gateway-address-routability-cluster` while keeping the infrastructure metadata permissions until cleanup has finished.

If the last usable ClusterIP is lost, the controller disables its own load balancer. It can reopen the same frontend when a usable address becomes available. [Local traffic and withdrawal](qualification/v1.7.0/provider/gateway-infrastructure.md#experimental-clusterip-reachability)
